# Native SSH connections and consistent machine names

## Credential and host identity boundaries

Inspect the existing legacy catalog and SSH configuration before connecting. WSL SSH and Windows OpenSSH have separate home directories, configs, agents, and known-hosts files. A WSL SSH success does not verify native Windows SSH.

Verify server host keys against an already trusted record; never disable host checking to make installation work. A dedicated Windows known-hosts file may contain verified public host keys. Public host keys are not private credentials.

Test the exact Windows alias with `ssh.exe -o BatchMode=yes ALIAS HARMLESS_COMMAND` before `hc machine add`.

If Windows cannot use a WSL private key due to UNC filesystem permission checks, do not weaken the private key's permissions. Obtain the user's choice before copying credentials or changing authorized access. A dedicated Windows key can be generated by Windows OpenSSH so its ACLs are native. Authorize only its public key on explicitly approved accounts, preserving all previous authorized keys; verify new-key access. Do not print private key material.

Preserve existing Windows SSH configuration. Add bounded aliases using explicit HostName, User, IdentityFile, IdentitiesOnly, StrictHostKeyChecking, and a trusted UserKnownHostsFile as needed. Avoid overwriting unrelated aliases. Keep any backups private.

## Command-based connection limitation

The tested Windows core 0.1.18 listed `--via` in help but rejected command-based connections on Windows. Source `machines.rs::check_target` explicitly rejected `cfg!(windows)` for this transport. Do not assume a newer build has the same limitation, or that help alone proves support.

Use ordinary Windows SSH aliases when command-based WSL SSH forwarding is unsupported. Do not modify source or install a replacement core merely to bypass the transport check.

## Native and legacy names

Native core may require lowercase machine identifiers. Preserve the user's requested name exactly; validate it and ask if it fails the installed rules. Display names and SSH aliases need not be identical, but record their mapping explicitly.

Only rename the legacy saved machine when requested. Discover its actual profile ID and use installed help. The tested legacy 0.9.5 parser required positional ID first even though help's usage rendering placed the option first:

    herdr machine rename EXACT_PROFILE_ID --label REQUESTED_NAME
    herdr machine list --json

Do not guess an ID from sidebar order, silently fix a misspelled source label, or delete/re-add the machine to rename it. Verify the same profile ID, SSH target, and remote session remain after renaming. Use the new label in subsequent `--machine` commands. Do not rename hostnames, remote accounts, or SSH aliases unless separately requested.
